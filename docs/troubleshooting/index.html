Troubleshooting

Having issues with SAT? This guide will help you resolve common problems. Click on any issue below to see the solution.

Checking your setup​

Built-in requirements check

Instead of standalone diagnosis notebooks, the app has a built-in requirements check. Open Settings → Re-run setup (or the first-run setup screen) and review the requirements checklist — it verifies, live, the account connection and the service principal's Account admin role, and flags configuration gaps so you can fix them before running collection. For a failed collection, open the Data Collection page and inspect the job's last run.

Common Issues​

Symptom: Account/Workspace/Metastore Admin detection, account users & groups, and other account-wide reports are empty, or the setup screen reports the credentials didn't verify.

Resolution:

Account credentials are stored as Unity Catalog secrets (SAT no longer uses a sat_scope secret scope). In the app, open Settings → Account credentials (or re-run setup) and confirm:

  • the Account ID is correct, and
  • the service principal's client ID + secret are valid and that SP holds the Account admin role.

Credentials are verified before they're stored, so a failed save points to one of the above. After updating them, run data collection again from the Data Collection page.

Symptom: account-wide reports stop updating, or a collection run fails authenticating to the account API — the service principal's OAuth secret has most likely expired or been revoked.

Resolution:

  1. In the account console, create a new OAuth secret for the service principal.
  2. In SAT, open Settings → Account credentials, paste the client ID and the new secret, and click Update credentials (verified before being stored as Unity Catalog secrets).
  3. Run data collection again. The jobs read the secret at run time, so the next run uses the new value — no redeploy or re-provision needed.
  4. Revoke the old secret in the account console.

The setup requirements check (Settings → Re-run setup) verifies the account connection and the Account admin role live, so re-run it to confirm the fix is green.

Symptom: A workspace you expect to see has no findings, or a scan run reports it as skipped.

Resolution: SAT scans a workspace only when both are true:

  1. The service principal is a workspace admin there, and the workspace is enabled. Scan coverage is keyed on the SP being a workspace admin of each workspace. Add the SP as a workspace admin on the target, then run Data Collection → Manage → Sync workspaces — Sync lists the account's workspaces and sets analysis_enabled on the ones the SP administers (account_workspaces table). Removing the SP as admin and syncing again drops the workspace.
  2. Collection scope is Multiple workspaces. With scope set to This workspace only, both resource collection and secret scanning stay on the current workspace regardless of what's enabled. Set scope to Multiple workspaces in Data Collection → Manage.

On serverless compute, reaching a remote workspace also requires the account to be enrolled in serverless cross-workspace access (a preview — ask your account team). Workspaces that still can't be reached are skipped and recorded, not failed. Classic compute can reach any workspace the SP administers.

The Permissions Analysis app uses on-behalf-of-user (OBO) authentication. The required sql scope is declared in the SAT install templates, but each user must consent to the scope on first open after the upgrade. If you opened the app before upgrading, your browser session has a cached consent grant without sql and you'll see the banner.

Resolution (try in order):

  1. Open the app URL in a private/incognito window — this triggers a fresh consent prompt.
  2. Or clear cookies for the workspace domain in your regular browser, then reopen the app.
  3. Or revoke the prior authorization from your account profile (if your workspace exposes a "Linked apps" list), then reopen.

The full background and permanent setup is on the Permissions Analysis page.

The app runs Statement Execution as the calling user, so Unity Catalog enforces the user's grants on the Permissions Analysis tables. If the user does not have SELECT on those tables, the app renders a friendly banner instead of a SQL error.

Resolution: an admin grants SELECT on the three tables to the user or group that needs to use the app. Replace <catalog> and <schema> with the values used during your SAT install:

GRANT SELECT ON TABLE `<catalog>`.`<schema>`.brickhound_vertices             TO `<admin_group>`;
GRANT SELECT ON TABLE `<catalog>`.`<schema>`.brickhound_edges                TO `<admin_group>`;
GRANT SELECT ON TABLE `<catalog>`.`<schema>`.brickhound_collection_metadata  TO `<admin_group>`;

The SAT SDK wheel ships inside the app (under lib/) and is installed with --no-deps, so no PyPI access is needed for the SDK itself. Two things still reach out, and only matter for the features that use them:

  • Secret scanning downloads the TruffleHog binary from GitHub. In a restricted-egress environment, allow-list raw.githubusercontent.com, github.com, release-assets.githubusercontent.com and objects.githubusercontent.com (all HTTPS/443 — the download redirects across them, so an incomplete list still fails; see the Secret Scanning firewall list) or provide an internal mirror.
  • Classic compute pip-installs requests and PyYAML from PyPI for the scanners (serverless already has them). On classic compute without PyPI access, make those available from an internal package index.
